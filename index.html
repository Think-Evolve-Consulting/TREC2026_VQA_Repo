Hi, I'm Aakash Gupta, from ThinkEvolve Consulting.

The question in the title is one I think most people in this room have asked at some point. You've got several models watching a video, they disagree about the answer, and the obvious thought is: get them to vote. Or argue it out. Surely that beats just picking one.

We spent about five weeks finding out, on one graphics card, with open models, across both tasks of the track.

I'll do the system and the answer-generation task first, because that's where our habit of measuring everything came from, and then give the second half of the talk to the debate question itself.

Setup

The dominant risk was not a weak model. It was a silent failure.

One GPU

An RTX 3090, 22.7 GiB usable. No two models fit at once, so every “agent” is a sequential pass with a teardown and reload in between.

Open weights, local

No hosted APIs. One larger model was rejected because it could only run through an API, which would have sent track data to a third party.

Little time

Answer generation closed 17 August 2026; multiple choice closed 18 September.

A run that completes, validates and is wrong: a model answering with no video attached, a frame budget silently disabled, a dev query scored against the wrong year's questions.

Rule: no component entered a submission without a measured gain on labelled 2025 data, under a test fixed before the numbers were read. One exception, the answer-generation ensemble, and we'll see how it turned out.

Notebook paper §1, §32

Three constraints, quickly.

One graphics card, the consumer kind. Every model we used fills it completely, so they run one at a time, in a queue. When I say multi-agent later on, that is what it means: load a model, run it over everything, save the answers, unload it, load the next one. There is no live conversation anywhere in this.

Open models only, nothing hosted, because the data had to stay on our machines. And about five weeks.

Click

Given all that, the thing that actually kept me up wasn't that some model would turn out to be weak. It was that a run would finish, pass every check we had, and be wrong anyway.

All three of the examples on this slide happened to us.

So we made a rule. Nothing gets submitted unless we have measured that it helps, against a standard we wrote down before looking at the result. We broke that rule once, near the deadline, and I'll show you what it cost.

Self-reported confidence carried no information. 96.9% of 14,100 router judgements came back at exactly 1.0, none below 0.7. The original design's “debate when confidence < 0.85” trigger could never fire.

Here's the whole thing, quickly.

Anything that doesn't depend on which model is answering, we compute once and save. Two speech-to-text systems. Frames from the video. Ten reworded versions of every question. And a component that works out what each question actually needs: video or not, audio or not, how many frames.

One trap in there worth your time. The standard speech setup decides what language a video is in from the first thirty seconds, which is very often a title card with no speech in it at all. So we sample several points through the video instead, weighted by how long each stretch is. Before we did that, a two-second clip misheard as Welsh was outvoting a six-minute English documentary.

Then the models run one at a time. Three for the writing task, eight for multiple choice.

And this is the first of about four places where asking a model how confident it was turned out to be worthless. It said completely confident, almost every single time.

The gap we could not close

The official STS metric calls a 2013 web service that no longer responds. Dev measured METEOR and BERTScore only.

Notebook paper §55

Most of what follows is a negative result, so the method is doing a lot of work here. Give me forty seconds on it.

Our scoring code reproduces the official scoring question by question, so we knew we weren't quietly measuring something slightly different.

Everything ran next to a dummy. One that answers at random, one that's handed the right answer. If the random one ever scores well, your test is broken and you want to find that out early. Ours came out at 25.3% where chance is 25, so we trusted the rest.

We wrote down what success looked like before we read anything. That sounds obvious. It isn't, when you're tired and the number is close and you really want it to be the number.

And every run reports how many questions it answered with the video actually attached. Not how many it answered. How many it answered properly.

Second task. Pick the right answer from a list. This is the panel: eight models, same job.

They all play by the same rules. They rank the option numbers rather than the text, so nobody wins by writing a nicer sentence. An unattended run is a different environment from an interactive one. Make every pass report its own evidence.

Twelve in the paper · Notebook paper §7.3, §910

Six of the twelve in the paper. Every one of these ran to completion and passed validation.

There's a setting controlling how much visual detail the model gets. We assumed it was per frame. It's for the whole video. So on long clips our model was effectively looking at thumbnails: 485 visual tokens where we'd planned for nearly eighteen thousand.

An error getting swallowed meant another model answered with no video.

And this one is my favourite. On Windows, if you ask for more graphics memory than you have, it doesn't fail. It quietly starts using system memory instead. So the card sits at 100%, the fans spin up, everything looks like it's working, and absolutely nothing is happening. We watched that for over ten minutes before anyone said anything.

Click

Nearly all of these got caught the same way. Every run counts its own evidence: videos attached, fallbacks used, input sizes. Boring, and it found almost everything.

Notebook paper §7.412

The first three attempts were all versions of voting.

Weight each model by how good it is and combine them: ties with just using the best one. Give them all equal say: three and a half points worse.

At that point we got stubborn. Every possible group of models, every weighting we could give them. Around 781,000 combinations.

Best one came out at 82.5% against 80 for the single model. Which looked great, for about a day.

Click

Because if you try 781,000 things, some of them are going to look good by accident. So we did it properly: pick the winner using most of the questions, then score it on the ones you deliberately kept back.

80.1%. Same as the single model. There was never anything there. We'd just found whichever combination got lucky on the questions we happened to be looking at.

Safety, verified

With two never-conceding mock agents, the output was SHA-256 identical to the baseline run. Also run end to end against the real InternVL judge.

Why no score

The Mac-hosted 27B judge could not return one answer in 30 minutes. Cost is ≈2.8 calls per disputed question, vs 3 for the baseline's vote.

Design after Du et al. 2023 · Notebook paper §7.616

So we designed one. Three rules, all straight off the last slide.

It only runs where the models disagree. Where they agree they're already 95% right, so leave it alone.

Two judges answer independently first. Then two rounds where they can hold or change their mind, but they have to point at a specific timestamp in the video when they do. No vague argument.

And if they still don't agree, we bin the whole thing and use the original model's answer. Not either judge's. The original. Because on these questions, remember, the original beat both of them.

Click

It also gets things the panel never had. More frames: 32 a video instead of about 14, and 64 for counting questions. An instruction to report the maximum count. And sound.

Click

And we checked that it can't hurt you. We ran it with two fake agents that refuse to ever concede, so every single question deadlocks, and the output came out byte-for-byte identical to the original run.

Click

And then we couldn't run it. We'd put the judge on a Mac and it couldn't finish one question in half an hour. We ran out of machine, basically. So that's where it sits: a design, and a measurement of how much room there is. It is not a result and I'd ask you not to treat it as one.

One place where none of this can possibly work: counting. How many people are in the shot, that kind of question.

Our best model gets 44% of counting questions wrong. Everything else, 17%. It's the only question type where the difference is big enough that we're confident about it.

Click

Which makes sense when you think about it. If the frames we handed the model don't actually contain the thing it's meant to count, arguing about those frames isn't going to produce it. So our fix gives it more frames. Not more argument.

Discussion

Measure what ships, with the metric that scores it

Dev transfers where the metric matches

Task 2 Top-1: within 0.3 points. Task 1: expansion lost STS, and we optimised a mean-over-ten scorer while 2026 scores rank 1.

Combination didn't rescue a weak panel

Six ways of combining models across both tasks. Each lost to or tied the best single model wherever measured.

Robustness beat capability

The one dedicated reasoning model finished last on both tasks, on output reliability. Gemma 4 won Task 1 largely by never failing.

Self-reported confidence was worthless

Router: 1.0 on 96.9%. Vote counts correlated negatively with correctness. Agreement across passes was the only useful signal.

Dev-set mismatch is the residual risk

Short-video, four-option dev sets hid the Qwen3-VL gap that 2026 exposed.

Gates saved compute

Muse Glimmer's failed gate saved 16–20 GPU-hours. Nested CV refused a +2.5-point in-sample winner.

Notebook paper §1019

The main thing: our testing predicted the official results well every time the thing we measured matched the thing they scored. Within 0.3 points on the second task.

Both of our surprises came from a mismatch. One metric we couldn't run at all, and scoring ten answers when only the first one gets read.

Combining models never beat the best single model. Not on either task, not once, across five different attempts and 781,000 searched variants.

Being reliable mattered more than being clever. The one model in our set built specifically for reasoning came last on both tasks, purely because of how often its output was unusable.

Asking a model how confident it is was useless everywhere we tried it. What did work was checking whether separate runs agreed with each other: 46% error when they disagreed, 14% when they agreed.

And writing the success criteria down in advance saved us real time. One model failed its test early and we never ran it over the full set, which is about twenty hours of GPU time we didn't spend for nothing.

Conclusion

Each next step comes from a measured weakness

  1. CountingEvery model undercounts, systematically (Qwen3.8: 43.8% error vs 16.8%). Denser frames and report-the-maximum are built, unmeasured.
  2. Audio evidence“What can be heard” questions on video whose audio the ranker never received. CLAP option scoring is built, not yet scored against labels.
  3. Rank-1 selection for Task 1Develop against @1; use generation log-probabilities or a trained reranker.
  4. Measure debate on dev203 disputed queries, same gate as the single judge.
  5. A local STSSo length-oriented changes are caught before submission.

So. One consumer graphics card, open models, five weeks. Our best multiple-choice run landed mid-field and matched what we'd predicted it would do. On the writing task our sets of answers were competitive; our choice of which one to put first was not.

Disagreement usually means the question is hard, not that one model knows the answer

  • Before building fusion or debate, compute wins and losses against your leader on dev. If every member loses on net, voting adds error.
  • Combination is worth trying when agents bring different evidence: more frames, audio, text. More opinions over the same 16 frames did not help.
  • Running locally made the controls free: null judges, a 781,248-fusion search, cached reruns. Next: debate on the 203 disputed dev questions, on the 3090, under the same gate.

If someone wants one slide to take away, it's the five checks here. Was the gate written first? Were there null and majority controls? Was there a paired test? Nested cross-validation if you searched? And a held-out confirmation?

Fifteen-minute talk, both TREC 2026 VQA tasks, plus questions. Target times per slide sum to about 14:30. Plain text is what you say; cues in amber mark clicks. Q&A preparation follows the script.

Q&A preparation

So debate would score 0.843?
No. That's what you'd get if you always picked whichever judge happened to be right, which isn't something you can actually do. It's a ceiling. We never ran debate properly. Backup B2.
Are you saying debate doesn't work?
No, something narrower. On our panel, where one model is clearly ahead of the rest, nothing we measured beat it. Debate we didn't measure. With models closer together you might well get a different answer.
Why didn't you run it?
We ran out of machine, basically. The judge was hosted on a Mac and couldn't get through one question in thirty minutes. On our own card it's a single overnight run, and that's next.
Why is your first-task score below the median?
We developed against last year's scorer, which averages all ten answers, so the order never mattered and we put the effort into filling all ten slots. This year only the first one counts. Best-of-ten we're 9th of 44; first answer, 23rd. And we had no reliable way of telling which of our answers was the good one. Backup B1.
Why ship the rewriting if it hurt a metric?
It passed the test we'd written, on the metrics we could actually run: the main one up everywhere, nothing else down, and it beat the padding control. The one it hurt we couldn't compute, because that service has been offline for years. We also submitted the version without rewriting, and that's our best run on that metric.
Did the reranking in the first task help?
It moved things by a few thousandths. We can't distinguish that from noise without per-question results. We submitted it on the design rather than on a measurement, and I'd call that a mistake.
Why did Qwen3-VL drop 4.9 points after tying on your set?
Our set was four options and short clips. The official one is mostly eight options with some very long videos, and it was routed. It came apart on what we couldn't test. Official comparisons are totals only, so they're unpaired, standard error about 0.8 points a run.
If the answer's in the panel 93% of the time, shouldn't voting work?
That tells you it's in there somewhere. For voting to find it, the other models need to be right specifically where they disagree with the best one. They aren't: every one of them loses more of those than it wins.
The judges overruled 39 and 61 times. Weren't they doing something?
They were doing plenty. Just not correctly. 16 fixed and 17 broken; 24 and 27. And our random judge scored where random should, so the setup wasn't handing out free wins.
Then why would debate help at all?
It might not. Two reasons it has a chance: it sees frames and audio the panel never got, and when the two judges split, one of them is right 38 times out of 50. Whether an argument can find that one, I don't know.
Does combining work for other teams?
Possibly, and it sharpens the point. Going by run names only, so I may have this wrong: teams whose models were close in ability seem to have gained, and teams with one clear leader lost. Which is what our table predicts. If anyone here is from one of those teams, I'd like to know whether I've read it right. Backup B4.
Is the combined run's official loss significant?
Not on its own. We only have totals, no per-question results, so a proper paired test isn't possible. It's consistent with what we predicted, and that's as far as I'd go.
Is 150 or 400 questions enough?
Only for big differences. Below about four and a half points, no. Two runs answering at random differed from each other by three.
Was any model's confidence useful?
No, and we checked everywhere. One component said maximum confidence 97% of the time. Another returned zero on every single answer. What did work was agreement between independent runs: 46% error when they disagreed, 14% when they agreed. Good as a warning, useless for deciding what to do, because every other model errs on those same questions too.
Why did Cosmos do so badly?
Not its eyesight. Unusable output on 19% of questions, 45% answered with no video because of a filename bug, and it's built to pick one answer rather than rank them all, so it needed a second call on 38% of multiple-choice questions.
Most useful single practice?
Making every run count its own evidence: videos attached, fallbacks used, input sizes, position bias. That's how we caught most of the twelve silent failures.
Why not a bigger or hosted model?
The data had to stay on our machines, so open weights and local inference were a constraint. One larger model was rejected because the only practical way to run it was a hosted API. And locally, re-running costs nothing, which is what paid for all the checking and the 781,000-combination search.
How did a 27B model fit on 24GB?
Compressed to 4-bit. Windows permanently holds about 1.3GB, leaving roughly 22.7. Nothing else fits beside it, so everything loads and unloads in turn.
Why does every model undercount?
We don't know. 44% wrong on counting against 17% elsewhere, nearly always too low. Our guess is the frames miss the busiest moment. We built a fix and haven't measured it.
How did you handle other languages?
Two speech systems. One only knows five languages, and 182 of our videos are in none of them, so Hindi came back as Korean in 36 of them. For the other we sample several points through the video rather than just the opening, weighted by how long each stretch is, because otherwise silence gets confidently labelled Norwegian.
Can anyone reproduce this?
Every stage saves its results, so you can re-run any part without redoing the inference. Random seeds come from the question text itself. We have standalone versions of six of the rankers that run in Colab.
Is a single-GPU result relevant if you have a cluster?
The scores obviously are limited by the hardware. The lessons aren't. Twelve of our failures produced output that looked completely fine, and that will happen to anyone.
Which problem would you warn people about first?
The visual-detail setting that covers the whole video rather than each frame. We were sending thumbnails and had no idea.
What would you do differently?
Develop the first task against the metric that actually scores it, from day one. Get a local version of the missing metric before tuning anything for length. Make the wins-and-losses table in week one. And always do the full end-to-end rehearsal: three of our multi-hour restarts were process problems, not model problems.
Which model would you recommend?
Multiple choice, Qwen3.8 at 4-bit: 80% on ours, 80.3 official. Writing task, Gemma with the ten-separate-questions approach.
Will you release the code?
Decide before the talk. Safe answer: every stage is re-runnable from saved results, and the paper documents every check and every trap we hit. Come find me afterwards.
